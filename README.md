# Hearth

Hearth is an open-source property management platform for management companies, covering tickets, properties, residents, meters, billing and payments, with an extension system for mini-apps.

## What This Project Does

Companies that manage residential buildings have to deal with resident requests, building data, utility meters, receipts and payments, staff and contractors. These usually end up spread across spreadsheets and separate tools. Hearth puts them in one web application with a GraphQL API that mobile apps and third-party services can use too.

It is built for property management companies, their employees (dispatchers, technicians, accountants) and developers who extend the platform with their own mini-apps.

Main features:

- **Tickets**: resident requests with statuses, deadlines, comments, files, auto-assignment rules and property hints
- **Properties**: buildings with a visual map builder for sections, floors and units, plus property scopes for staff access
- **Contacts and residents**: resident contacts, contact roles and resident service consumers
- **Meters**: meters, meter readings and reporting periods, with import from spreadsheets
- **Billing and acquiring**: billing integrations, receipts, payments, multi-payments, recurrent payments and payment exports
- **Banking**: bank accounts, transactions, cost items and account reports
- **Marketplace**: invoices and service price lists for paid services
- **News**: news items for residents with push, SMS and email delivery
- **Notifications**: messages over email, SMS, push (Firebase, Apple, Huawei) and Telegram, from localized templates
- **Organizations and users**: organizations, employees, roles with fine-grained permissions, invites, phone/email auth and OIDC
- **Analytics and AI**: ticket analytics, reports and AI-assisted flows
- **Mini-apps**: B2B and B2C mini-apps embedded in the main UI and talking to it through a bridge library, with a developer portal to register and publish them

## How It Works

Hearth is a Yarn workspaces monorepo. The main application, `apps/hearth`, is a Keystone (v5, `@open-keystone`) server. It exposes a GraphQL API backed by PostgreSQL and serves a Next.js frontend from the same process. Background jobs (exports, imports, notifications, integrations) run in a separate worker process that reads tasks from Redis. Shared code lives in `packages/` and is built with Turborepo.

Each business area is a **domain** under `apps/hearth/domains/<domain>`. A domain contains its Keystone schema (models and custom GraphQL services), access rules, constants, GraphQL queries, React components and hooks, background tasks and tests.

```mermaid
flowchart LR
    U[Browser / mobile app] -->|GraphQL| N[Next.js pages + Apollo client]
    N --> K[Keystone GraphQL API<br/>domains/*/schema]
    K --> A[Access rules<br/>domains/*/access]
    K --> DB[(PostgreSQL)]
    K -->|enqueue tasks| R[(Redis)]
    R --> W[Worker<br/>worker.js]
    W --> DB
    W --> X[Email / SMS / push<br/>bank & billing integrations]
    M[Mini-apps] -->|@open-hearth/bridge| N
    M -->|OIDC + GraphQL| K
```

1. A user acts in the web UI (`apps/hearth/pages`), and an Apollo client sends a GraphQL query or mutation.
2. Keystone resolves it through the domain's list or service in `domains/<domain>/schema`, after checking the access rules in `domains/<domain>/access`.
3. Data is read from and written to PostgreSQL. Each schema change has a migration in `apps/hearth/migrations`, generated by `bin/kmigrator.py`.
4. Slow work is queued in Redis and handled by the worker (`apps/hearth/worker.js`), which also sends notifications and talks to external services.
5. Mini-apps run inside the UI and use `@open-hearth/bridge` to talk to it. On the server side they authenticate with OIDC.

## Tech Stack

| Layer | Technology | Purpose |
|---|---|---|
| Runtime | Node.js 24 | Runs all apps and packages |
| Package manager | Yarn 4.17 (workspaces), Turborepo 2.4 | Monorepo dependencies and build pipeline |
| Backend | Keystone 5 (`@open-keystone/keystone` ^19.4) | Data models, GraphQL API, admin UI |
| API | GraphQL 16, Apollo Client 3.11 | Client-server communication |
| Frontend | Next.js ^15.5, React 18.3, Ant Design 4.24 | Web UI |
| Language | TypeScript 5.8, JavaScript | Application code |
| Database | PostgreSQL 16.8 | Main data storage |
| Cache / queues | Redis 6.2, Valkey 8.0 (cluster mode) | Sessions, caches, background task queues |
| Messaging | NATS 2.12 | Real-time messaging |
| Migrations | Python 3 + Django 5.2 (`bin/kmigrator.py`) | Generating and applying schema migrations |
| Auth | Password, phone and OIDC (`oidc-provider`, `openid-client` 5.7) | User and mini-app authentication |
| Testing | Jest 29, ts-jest, k6 | Unit, schema and load tests |
| Linting | ESLint 8, Stylelint 14, Semgrep, commitlint | Code quality and commit message rules |
| Deployment | Docker, Docker Compose | Container image and local services |

## How to Run This Project

1. **Prerequisites**
   - Node.js 24 (`engines.node` is `>=24`)
   - Yarn 4 (Corepack: `corepack enable`; the repo pins `yarn@4.17.0` in `.yarn/releases`)
   - Python 3 with `Django` and `psycopg2-binary` (for migrations)
   - Docker and Docker Compose (for PostgreSQL and Redis), or PostgreSQL 16 and Redis 6 installed locally

2. **Clone**
   ```bash
   git clone https://github.com/abdullah6223/hearth-platform.git
   cd hearth-platform
   ```

3. **Install dependencies**
   ```bash
   yarn install
   pip install Django psycopg2-binary
   ```
   If `turbo: command not found` shows up in later steps, install it globally with `npm i -g turbo@^2`.

4. **Start the databases**
   ```bash
   docker compose up -d postgresdb redis
   ```
   PostgreSQL listens on `127.0.0.1:5432` (replica on `5433`) and Redis on `127.0.0.1:6379`.

5. **Build the shared packages**
   ```bash
   yarn workspace @app/hearth build:deps
   ```

6. **Environment variables**

   The prepare script copies `.env.example` to `.env` (globally and for each app) and writes the per-app values below. You only need to edit `.env` by hand for optional integrations.

   | Variable | Description | Example |
   |---|---|---|
   | `DATABASE_URL` | PostgreSQL connection string for the app | `postgresql://postgres:postgres@127.0.0.1/local-hearth` |
   | `REDIS_URL` | Redis connection string | `redis://127.0.0.1/1` |
   | `PORT` | HTTP port of the app | `4001` |
   | `SERVER_URL` | Public URL of the app | `http://localhost:4001` |
   | `HEARTH_DOMAIN` | URL of the main app, used by other apps | `http://localhost:4001` |
   | `DEFAULT_LOCALE` | Default UI language | `en` |
   | `FILE_FIELD_ADAPTER` | File storage adapter | `local` |
   | `USE_LOCAL_FEATURE_FLAGS` | Use static feature flags instead of a remote service | `true` |
   | `DISABLE_CAPTCHA` | Turn off captcha checks locally | `true` |
   | `NOTIFICATION__SEND_ALL_MESSAGES_TO_CONSOLE` | Print notifications instead of sending them | `true` |
   | `MESSAGING_CONFIG` | NATS messaging settings (JSON) | see `.env.example` |
   | `FIREBASE_CONFIG_JSON`, `APPLE_CONFIG_JSON`, `HMS_CONFIG_JSON` | Optional push notification credentials | `<your-credentials>` |
   | `EMAIL_API_CONFIG` | Optional email provider settings (JSON) | `<your-config>` |
   | `AI_FLOWS_CONFIG`, `AI_ADAPTERS_CONFIG` | Optional AI flow settings (JSON) | see `.env.example` |

   See `.env.example`, `apps/dev-portal-api/.env.example` and `apps/dev-portal-web/.env.example` for the full list.

7. **Database setup**

   This creates a database for each app, fills in the `.env` files, runs migrations and creates local test users:
   ```bash
   node bin/prepare -f hearth
   ```
   In a real deployment, set the variables yourself and run migrations with `yarn workspace @app/hearth migrate`.

8. **Run**

   Development mode:
   ```bash
   yarn workspace @app/hearth dev
   ```
   Production mode:
   ```bash
   yarn workspace @app/hearth build
   yarn workspace @app/hearth start
   ```
   Open the `SERVER_URL` printed by the prepare step (its port is stored as `PORT` in `apps/hearth/.env`, e.g. `http://localhost:4001`).

   Background worker, in a second terminal:
   ```bash
   yarn workspace @app/hearth worker
   ```

9. **Run tests**

   Tests run against a prepared local environment with the databases running:
   ```bash
   yarn workspace @app/hearth test
   ```
   Lint the whole repository with `yarn lint`.

10. **Docker**

    Start the full database set (PostgreSQL primary and replica, Redis) and build the app image:
    ```bash
    docker compose --profile dbs up -d
    docker compose --profile app build app
    ```
